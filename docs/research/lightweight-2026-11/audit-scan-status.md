# 审计报告：仓库扫描 / 状态读取 / 提交执行链路

任务 key：`audit-scan-status` · 只读审计，未改动仓库内任何文件（审计后 `git status` 为空）。
实验全部在 `/tmp/swarm/scanexp/` 下的自建临时仓库与探针里完成。

## 结论（先看这里）

1. **这条链路本身不慢，慢在「触发方式」。** 本机一次刷新约 70–110 ms，其中约 45 ms 是 git 进程启动；启动扫描热缓存 0.2–0.6 秒。真正的问题是**鼠标扫过侧栏每碰一行就起 2 个 git 进程，没有节流、没有上限、不可中断**（问题 1）。
2. **正确性缺口比性能缺口更该先修**：「双方新增」类冲突会被当成普通新增直接提交（问题 3）；带通配符字面的文件名会被当成模式连带暂存别的文件（问题 4）。两处都是 1–2 行改动。
3. **多余复杂度集中在两处**：文件列表的「智能分组」打分算法（约 200 行、11 个魔法数字）放在领域模型里且每次界面重绘都重算（问题 5）；若干成对重复的代码（问题 9）。
4. **git 自身的加速项（untracked cache、fsmonitor）在本机自建仓库上测不出收益**，不建议由本工具代用户改仓库配置（见「外部依据」）。
5. 状态解析**没有**跑在主线程上（探针已证伪这一怀疑），但项目设置一变就会悄悄回到主线程（问题 8 附注）。

## 六个问题的直接回答

| 问题 | 回答 | 证据 |
|---|---|---|
| 1 启动扫描 | 单线程递归，整体在后台任务里，扫描期间界面可操作。每个目录约 4 次文件系统调用。跳过规则只有「名字黑名单 + 首层以下的隐藏目录 + 符号链接 + 安装包」。**无卷边界判断**：外置盘 / 网络盘 / 云同步目录若以真实目录挂在 Home 下非排除路径就会被走进去。**无取消、无增量结果**：只防重入，结束时一次性整体替换；因不允许重入，也就不存在过期结果 | `Services/GitRepositoryScanner.swift:44`、`:84`、`:90`、`:92`、`:105-123`、`:111`、`:125-135`；`Stores/RepositoryStore.swift:28`、`:38` |
| 2 状态读取 | 每次选中仓库、手动刷新、回到前台都启动 **2 个** git 进程**并行**：`status --porcelain=v2 --ignored=matching --untracked-files=all -z` 与 `ls-files -t -z`，全局带 `--no-optional-locks`。两者都用 `-z`，特殊字符路径安全；解析在后台线程；重命名记录的原路径按 NUL 续读。**无防抖**；选中仓库的加载任务可取消，但**只丢弃结果、不杀进程** | `ContentView.swift:51-57`；`Services/GitRepositoryStatusLoader.swift:6-19`、`:117-123`；`Services/GitCommandSupport.swift:33`；`Stores/RepositoryStatusStore.swift:30` |
| 3 文件监听 | 没有。新鲜度靠：选中仓库、手动刷新、应用回到前台、文件级操作与提交完成后的回调刷新 | 全仓库搜索文件监听与定时器相关 API，仅 diff 视图与网络请求各有自己的超时 |
| 4 提交 / 推送 | 最多 **5 个串行** git 进程：取消暂存被排除项 → 暂存 → 检查暂存区是否为空 → 提交 → 推送。整体在后台任务里，不卡主线程，但期间侧栏和文件列表被禁用。提交失败弹窗；推送失败弹窗并说明「本地已提交」。**无超时、无取消、无进度** | `Services/GitRepositoryCommitService.swift:22`、`:35-66`、`:99`、`:164`；`ContentView.swift:84`、`:122`、`:173` |

| 6 git 性能特性 | 见「外部依据」 | — |

## 问题清单（按影响排序）

### 1. 悬停预取无节流、无上限、不可中断 — 高

| 项 | 内容 |
|---|---|
| 证据 | 鼠标进入侧栏任意一行即触发预取（`Views/Sidebar/RepositorySidebar.swift:141-145`）；预取只查「该仓库是否已有缓存或任务」（`Stores/RepositoryStatusStore.swift:86-95`），不同仓库之间无数量限制、不取消前一个；每个预取 = 2 个 git 进程 + 阻塞式读管道（`Services/GitCommandSupport.swift:55-56`），占住 2 个后台协作线程 |
| 影响 | 鼠标扫过 40 行 ≈ 瞬时起 80 个 git 进程；协作线程池宽度与核数同量级，占满后应用内所有后台工作（含 diff 加载）排队。大仓库一次 `status` 可达秒级。卡顿程度未做运行时实测，触发路径已由代码确认 |
| 建议 | 悬停停留约 200 ms 才预取；同时最多 1 个在途预取，新目标到来时丢弃旧目标结果 |
| 改动量 | 小，约 20 行（`RepositoryStatusStore.prefetch` 与侧栏行悬停回调） |

### 2. 提交 / 推送可能无限期等待，中途失败不恢复暂存区 — 高

| 项 | 内容 |
|---|---|
| 证据 | 全仓库搜索不到超时或终止子进程的逻辑；`Services/GitRepositoryCommitService.swift:71-104` 先改暂存区再提交，任一步失败直接抛错返回，无回滚；`ContentView.swift:84`、`:173` 提交期间禁用侧栏与文件列表 |
| 影响 | (a) 推送卡在网络或预推送钩子上时，整个工作区不可操作也无法取消；(b) 用户在别的工具里暂存好的内容会被本工具改写，若随后提交失败，暂存区停在「被改了一半」的状态（内容不丢，只是暂存标记变了） |
| 建议 | (a) 加「取消」入口，命令执行器支持中止子进程；(b) 记录被取消暂存的路径，失败时原样恢复 |
| 改动量 | (a) 中，约 40 行；(b) 小，约 15 行，但是产品取舍，见「需要先设计」 |

### 3. 「双方新增」冲突被当作普通新增提交 — 高（正确性）

| 项 | 内容 |
|---|---|
| 证据 | 冲突判定只认字母 U（`Domain/RepositoryFileModels.swift:90-92`、`Services/GitRepositoryStatusLoader.swift:156`）；实测该场景状态码为 `AA` |
| 影响 | 这类冲突文件显示成「新增」、可勾选、默认提交；提交时被直接暂存并提交，等于用工作区里带冲突标记的内容「悄悄解决」了冲突 |
| 建议 | 冲突判定补 `AA`，加一条带合并冲突的测试固件 |
| 改动量 | 极小，2 行 + 测试 |

### 4. 提交时的路径被当成通配模式 — 中（正确性，低频）

| 项 | 内容 |
|---|---|
| 证据 | 路径经 `--pathspec-from-file` 传入且未加字面量前缀（`Services/GitRepositoryCommitService.swift:160-166`）；实测字面文件名 `*.txt` 会连带暂存其它文件 |
| 影响 | 文件名含 `*`、`?`、`[` 或以 `:` 开头时可能多暂存或报错。日常罕见，一旦发生是「提交了不该提交的东西」 |
| 建议 | 每条路径前加 `:(literal)` |
| 改动量 | 极小，1 行 + 测试 |

### 5. 「智能分组」算法放错层，且每次重绘重算 — 中

| 项 | 内容 |
|---|---|
| 证据 | 约 200 行打分逻辑在领域模型文件里（`Domain/RepositoryFileModels.swift:258-463`，打分阈值与系数共 11 个魔法数字，如 `:391-409`）；它在视图构建过程中被调用（`Views/RepositoryStatus/RepositoryFilePanel.swift:121`）；悬停状态存在被主视图读取的可观察容器里（`Stores/WorkspaceSelectionStore.swift:17`、`ContentView.swift:92`），鼠标每划过一行文件就重新分组一次 |
| 影响 | 文件多的仓库里，鼠标在列表上移动时主线程反复做字符串分组与标题压缩，可能掉帧；算法难维护、没有任何测试覆盖。掉帧程度未做运行时实测 |
| 建议 | 分组结果随快照算一次并缓存（在后台算），或退回「按直接父目录分组」 |
| 改动量 | 缓存版小到中，约 30 行；简化版需先定产品规则 |

## 已核实「不是问题」的部分

- 扫描与状态读取都不占主线程；状态解析在后台线程（探针验证）。
- `-z` 用得正确，带空格、中文、引号的路径不会被拆坏；被忽略的目录会被 git 整体折叠上报，「忽略的文件」列表不会爆炸（实测输出）。
- `--no-optional-locks` 让读取状态不抢索引锁、不改写索引（本机 `man git` 原文）。
- git 的警告文字混进输出时会被解析器当作无关记录跳过（实测「目录无权限」警告），不会损坏列表。
- 命令执行器对「先写输入再读输出」的死锁已有防护，并有专门测试。

## 外部依据

**本机一手来源（已核对）**

- `man git-status`（本机 git 2.51.2）：性能一节写明 `core.untrackedCache` 与 `core.fsmonitor` 的作用是「只搜索上次之后变过的目录」；`--ignored=matching` 下被忽略的目录整体上报。本机自建仓库实测在 2 千 / 2 万已跟踪文件规模上两者都没有可测出的收益，量级被进程启动时间盖过。
- `man git`：`--no-optional-locks` 等价于关闭「需要加锁的可选操作」。
- `man git-add`：`--pathspec-from-file` 与 `--pathspec-file-nul` 的语义；路径按模式解释这一点由本机实验确认。
- Swift 线程归属：本机探针（Xcode 自带 Swift 6.4.2，语言模式 6 与 5 各跑一遍）。

**检索配额用尽前取得的一手页面**

- `https://git-scm.com/docs/git-status`（检索摘要，内容与本机 man 一致）：untracked cache / fsmonitor 的官方说明。

**未核对（检索配额用尽）**

- 其它 git 客户端是否默认帮用户开启 untracked cache / fsmonitor：未查到一手资料，不作结论。
- 「大仓库上悬停预取会造成可感知卡顿」的具体阈值：未做运行时实测，属未验证假设；触发路径已由代码确认。
