## 一、结论

| 闸门 | 结论 | 依据（已验证） |
|---|---|---|
| G1 单栏滚动 | PASS（代理） | 1 万 / 5 万行各 3 次：相邻节拍主线程开工间隔中位数 16.67 毫秒；超 34 毫秒占比 1 万行 0%，5 万行 0% / 0.5% / 0% |
| G2 并排同步滚动 | FAIL（代理） | 本次写的并排承载 1 万行：每拍主线程工作约 1.24 秒，10 秒只完成 34 拍、合并 2388 拍；5 万行未跑。原因未定位 |
| G3 内存 | FAIL | 成因已定位（见第四节），但**没有拿到经实测的规避办法**；参考实现原样 1 万行跳转后 153–161 MB，超 150 MB |
| 真实上屏确认 | 未做 | 按主控要求不再让窗口上屏，留待用户不用电脑时补测 |

需要主控知道的三件事：

1. **上一轮「上不了屏」的根因不是系统策略，而是原型没有进入标准应用启动流程**。只手动驱动主运行循环时，应用不算启动完成，窗口永远进不了窗口服务器；进入标准启动流程后窗口立刻被判定在屏（最小对照 `logs/probe_result.json` 之前的两次探测 + 最小程序对照，已验证）。
2. **在收到调整通知之前，有两次各 3 秒的运行真的上了用户屏幕**（经系统启动、1 千行、3 秒滚动，`logs/smoke_g1_*`，另有 1 次用旧二进制重复）。这两次的数字不满足规程，**未用于任何判定**，仅如实登记：3 秒 180 拍、相邻绘制 16.4–16.8 毫秒、单次绘制 0.6–0.7 毫秒、结束时占用 170 MB。此后全部改为离屏，每次运行都记录了「窗口在屏 = 否、应用未启动」。
3. **并排承载（G2）和单栏（G1）差距达 200 倍**，是视图层实现前必须先解决的问题，不是测量噪声。

原样 1 万行跳转后 153–161 MB（中位 157），**未达 ≤ 150 MB**。G1/G2 跑完 10 秒滚动后占用 177–213 MB。

### 成因（已验证）

跳转前后按区域类型对比，首屏 → 跳到末尾增加的是：

| 区域类型 | 首屏 | 跳到末尾后 |
|---|---|---|
| 图形所有内存（owned unmapped (graphics)） | 0 | 98.1（46 块） |
| IOSurface | 0 | 12.0 |
| 图形加速内存（IOAccelerator） | 0.1 | 3.9 |
| 普通堆（MALLOC_SMALL + 默认区） | 16.3 | 20.9 |

全量 `vmmap` 显示图形所有内存是 **24 块 × 4 MB（= 1024×1024×4 字节）** 加若干小块——即按 1024 像素见方分块的位图。它与行数无关（1 千行同样 +127 MB），与视图高度和「滚到过哪些区域」有关：把文本视图高度钉在一屏后，同样的跳转调用只增加 0.3 MB。

结论：参考实现把文本视图撑成文档全高（1 万行 16.5 万点、5 万行 82 万点），系统为这个视图的图层后备按到过的区域分块分配位图，滚过的地方不回收。这是**图层后备存储**，不是差异算法或文本排版数据。

### 规避办法

- **已验证无效**：「并入视口层绘制」（文本视图自带图层，是这种做法的明文例外，1 次设计性失效 + 实测无变化）；「分块图层」（跳转后更差，187 MB）。
- **方向正确但未实现、未实测**：不要让文本视图等于文档全高——视图保持一屏高，滚动位置交给文本系统的视口排版控制器去驱动。这是本机 SDK 文本系统设计的做法，但需要另写滚动与跳转逻辑，本轮没有时间做。
- 因此 G3 判 **FAIL**：成因清楚，规避办法未经验证，判据未达标。
