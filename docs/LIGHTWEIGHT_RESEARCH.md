# NeatGit 轻量化调研：差异展示的技术路线

> 状态：**调研结论，方向未定**。调研日期 2026-11-26，由 9 路并行调研汇总而成，关键数字均经主控复核。
> 单位：本文 MB 按十进制；原始报告混用 1024 进制，两者相差约 5%，不是矛盾。
> 调研时本机工具链实测为 macOS 26.7 / Xcode 27.2 / Swift 6.4（项目说明里写的仍是 Xcode 26，见[待决策](#七待决策清单)第 10 项）。

## 一、结论摘要

1. **「重」集中在差异展示这一处。** 应用包约四分之三的体积是内嵌网页编辑器的资源；应用一启动就常驻 4 个进程，其中 3 个是为网页服务的系统辅助进程。原生代码只有约 7 千行、零第三方依赖。
2. **专业级差异视图不需要内嵌代码编辑器。** 10 款主流客户端里只有 GitKraken 把 Monaco 打进了包；原生派全部用系统文本能力或自绘，语法高亮拆成一个只负责分词的小库。
3. **差异算法不用自己写，也不用引第三方库**：行级和行内高亮都可以直接让 git 算，应用只写解析器。
4. **三条路都能走通，区别在能不能去掉网页带来的固定成本。** 只有换原生能去掉 3 个网页辅助进程、本机监听端口和 Node 构建链；网页路线无论怎么瘦身，前两项都在。但**原生视图自身的内存优势尚未证明**（见第 6 条）。
5. **与路线无关、应先修的问题比轻量化更要紧**：两处会提交错内容的正确性缺陷，以及鼠标划过侧栏就大量启动 git 进程。
6. **原型实测：原生方案在万行级够快。** 5 万行首屏约 0.12 秒、跳转约 0.03 秒、每滚约 0.65 屏主线程约 4.5 毫秒，几乎不随行数变化。遗留两个问号：真实上屏帧率未测到（全是离屏绘制）；跳转后有一笔约 120 MB、与行数无关的内存增长来源未定位。详见[第四节](#4-原生渲染可行性)。

## 二、现状基线（实测）

测量对象是临时目录里构建的副本，运行时指标取自调试构建，机器当时负载较高，**内存与进程数可靠，耗时类数字只代表量级**。

### 包体

| 项 | 正式构建 |
|---|---|
| 应用包 | 16.8 MB |
| 其中内嵌网页资源 | 约 12.8 MB（74%），94 个文件 |
| 　其中 5 个语言后台脚本 | 8.39 MB（TypeScript 一个就 5.76 MB） |
| 　其中页面主脚本 | 3.51 MB |
| 　其中 85 个语言定义文件 | 合计 0.52 MB |
| 自家代码二进制 | 4.3 MB |
| 第三方依赖 | 0 |

这些文件平时并不全部加载：打开 Swift 文件只加载主脚本、编辑器基础脚本和一个几 KB 的语言定义；只有打开 js/ts/css/html/json 文件才拉起对应的大脚本。**重首先是包体，其次才是运行时。**

### 运行时

| 状态 | 进程数 | 合计常驻内存 |
|---|---|---|
| 刚启动、未选任何仓库 | 4 | 204–225 MB |
| 选中一个仓库 | 4 | 233 MB |
| 第一次显示差异 | 4 | 285 MB（渲染进程 124 → 169 MB） |
| 看 170 KB 文件 | 4 | 407 MB（瞬时峰值 480–656 MB） |

- 4 个进程：应用主进程约 72 MB、网页渲染约 124 MB、图形约 14 MB、网络约 11 MB。后三个在启动后约 1 秒出现，**早于任何用户操作**——差异视图在界面里常驻，占位提示盖在它上面。
- 窗口约 1.1 秒出现（热启动中位数；冷启动 2.0 秒仅 1 次样本）。启动速度不需要优化。
- 启动到空闲消耗 1.6–2.6 核·秒。
- 再次查看看过的文件，耗时与首次相当，缓存没有带来可见加速。

### 扫描与状态读取

- 一次刷新约 70–110 ms，其中约 45 ms 是 git 进程启动；启动扫描（磁盘缓存已热）0.2–0.6 秒，发现 46 个仓库。这条链路本身不慢。
- 慢在触发方式：鼠标每划过侧栏一行就启动 2 个 git 进程去预读，无停顿阈值、无数量上限、不可中断。划过 40 行约等于瞬时 80 个 git 进程。

## 三、三条路对比

| 维度 | (a) 换原生渲染 | (b1) 保留编辑器、只裁剪 | (b2) 换轻量网页库 CodeMirror 6 | (c) 不动技术栈、只做优化 |
|---|---|---|---|---|
| 网页资源体积 | 0 | 12.8 → 3.0–3.4 MB | 0.25–0.97 MB | 不变 |
| 应用包（估算） | 约 5 MB | 约 8 MB | 约 5 MB | 约 17 MB |
| 网页辅助进程 | **去掉 3 个** | 不变 | 不变（推断） | 不变 |
| 本机监听端口 | 去掉 | 仍在 | 待定 | 仍在 |
| 空闲内存 | 约省 145 MB（按基线推算） | 基本不变（推断） | 基本不变（推断） | 仅「从不开差异」的使用过程能省 |
| 看差异后的内存 | **未证明更省**：首屏仅增 32–44 MB，但跳转后另有约 120 MB 来源待定位 | 不变 | 不变（推断） | 不变 |
| 功能 | 需重建：并排、行内高亮、折叠未变更区域、外观主题；语法高亮建议第一步不做 | **全部保留** | 基本保留；Kotlin、Objective-C 无官方语法包；主题需重建 | 全部保留 |
| 改动量 | 删约 870 行 Swift、12.8 MB 资源、整套前端构建链；新增约 800–1200 行渲染代码，另加解析器与测试 | 入口改十几行 | 页面层约 300 行重写，Swift 侧少量 | 约 40–60 行 |
| 主要风险 | 真实滚动帧率与一笔内存增长待查；并排同步、行内高亮、折叠需自建 | 无 | 大文件默认差异精度下降（调参可恢复） | 无 |
| 做完之后 | 去掉 Node 构建链，干净检出可直接出包 | 仍需 Node 构建链 | 仍需 Node 构建链 | 同左，另可解决监听卡死无超时 |

**主控建议（供决策，不是既定方案）**：分两步走。

1. **先做「哪条路都要做」的速赢包**，不依赖方向：修两处正确性缺陷、悬停预读加停顿阈值、差异视图改成用到才加载、删约 220 行死代码。
2. **以把关结果选择方向**：把关未全部通过，已改走 (b2)（见第八节）；原生方案的两个未解工程问题解决并补做真实上屏验证后，可重新评估切回 (a)。不建议停在 (b1)——它只解决包体，解决不了运行时成本。

建议依据：项目原则是原生优先；[竞品调研](#1-主流竞品)表明原生做差异视图是业界常态、内嵌编辑器是少数派；[基线](#二现状基线实测)表明只有原生能动运行时内存；(b2) 的包体与 (a) 相当，但功能保留更完整，适合做退路。

## 四、各专题要点

### 1. 主流竞品

| 派别 | 代表 | 差异视图怎么做 | 下载包 / 解包后 |
|---|---|---|---|
| 原生派 | Fork | 系统文本视图，一组原生并排/单栏类 | **31 MB / 107 MB** |
| | Tower | 原生文本控件 + 随包一个 1 MB 的分词库做高亮 | 86 MB / 192 MB |
| | Sourcetree | 原生表格视图，包内没有高亮库 | 69 MB / 172 MB |
| | Sublime Merge | C++ 自绘 | 40 MB / 124 MB |
| 网页壳派 | GitHub Desktop | 只借一个分词器在后台算高亮，差异行自己画 | 513 MB |
| | GitButler | 自绘组件 + 分词库 | 47 MB / 111 MB |
| | GitKraken | **唯一把 Monaco 打进包的** | 218 MB / 691 MB |
| 终端派 | LazyGit、Magit | 砍掉语法高亮和并排 | 6.6 MB / — |

- 重量派重的是壳（自带整个浏览器），不是差异视图。原生也不等于自动小：Tower、Sourcetree 比 GitButler 还大。
- 差异视图的「刚需」没有共识：没有哪一项能力是 9 家全部具备的。语法高亮最接近共识（6 家有、3 家明确没有）；最轻的两家都砍掉了语法高亮和并排。
- 对照：NeatGit 现状是「原生壳 + 用网页承载全量编辑器做只读差异」，同类产品里没有第二家这个组合。

### 2. 网页路线的瘦身下限（本机实建复核）

| 档 | 资源体积 | 说明 |
|---|---|---|
| 现状 | 12.86 MB | 入口整包引入，固定带上 83 门语言和 5 个后台脚本 |
| 仅裁剪 | 3.08–3.40 MB | 现有在用功能实测全部保留；再往下压不动，编辑器最小核心本身 2.6 MB |
| CodeMirror 6 | 0.25–0.99 MB | 脚本内存约为前者的 1/3–1/2；页面层需重写 |
| diff2html、git-diff-view | — | 不合格：前者无虚拟滚动与折叠，后者必须配 React 或 Vue |

- CodeMirror 两个实测坑：默认配置下万行高重复度样本会误标六十余行改动（调 `scanLimit` 恢复）；接了语法包还要显式开启默认着色。
- 裁剪到没有语言后台脚本后，编辑器仍有一个基础脚本必须有网络地址才能启动，所以本机监听服务短期去不掉。
- 内存与耗时数字来自桌面浏览器无头模式，只代表量级。

### 3. 开源实现：没有现成组件，但有作业可抄

- 没有许可兼容、仍在维护、可直接引入的 Swift 差异视图组件。成熟实现都长在各自 App 里。
- **foldgit**（MIT，188 星，2026-10 新建、仍在提交）：调 git → 自己解析 → 原生渲染，并排、行内高亮、大差异默认折叠都有；相关代码约 1000 行，规模有参考价值。行内高亮用「行配对 + 有限字符比对」。
- **Maple**（MIT，57 星）：产品结构最接近 NeatGit，但只有单栏、无行内高亮。
- **GitUp**（1.2 万星）：最成熟的原生绘制，但许可证是 GPL，只能看思路。
- **Xit**（Apache-2.0）：保留网页方案但没用重型编辑器，网页资源合计约 32 KB。
- 借鉴 MIT 代码前要先确定本项目的许可证——仓库目前没有许可证文件。

### 4. 原生渲染可行性

- **系统没有现成的差异视图或代码视图组件。** 在本机 SDK 全部接口文件里检索行号、侧栏、语法高亮相关符号，命中为零。
- macOS 26 新增的富文本编辑器面向编辑：无只读开关、无行号栏、只能给文字区间上色不能整行铺满，帮不上差异场景。
- Apple 给出的「系统文本视图加行号栏」官方做法，所需接口要 macOS 27 才可用，本项目最低支持 26，暂时用不上。
- **可行路线**：系统文本视图（只读、可选）+ 自绘行号栏与整行底色。选择、复制、查找、辅助功能由系统接管，零依赖，体积增量为 0。
- 本机实测全文排版耗时：1 万行约 0.15–0.2 秒，5 万行约 0.7–1.0 秒——必须放到后台或只排可见区域。
- 语法高亮没有好的轻量选项：通用的现成方案要么仍是跑 JavaScript，要么全语言包 32.7 MB 比现在还大，通用的语法解析引擎每种语言要单独接入且接入失败过。**建议第一步只做增删着色。**
- 第三方组件 STTextView 功能最贴合，但许可证是 GPL 或付费商业授权。
- **验证原型实测**（一次性原型，合成数据，1 千 / 1 万 / 5 万行，增删行约 30%，3 次取中位数）：

| 承载方式 | 5 万行首屏 | 5 万行跳到末尾 | 每滚约 0.65 屏（主线程） | 结论 |
|---|---|---|---|---|
| 系统文本视图 + 自绘行号栏与整行底色 | 0.12 秒 | 0.03 秒 | 4.5 毫秒 | **首选**，三项几乎不随行数变化 |
| 纯 SwiftUI 懒加载行列表 | 0.09 秒 | 0.96 秒 | 11 毫秒 | 可用但偏慢，跳转随行数线性变慢 |
| SwiftUI 列表控件 | 1.2 秒 | 0.35 秒 | 14 毫秒 | 不建议，首屏与总行数成正比 |
| 系统新富文本编辑器 | **410 秒** | — | — | 出局，耗时随行数平方增长 |

- 原型里首选方案的视图本体约 132 行就做出了行号栏对齐、整行底色、折行续行不重复编号；唯一的实现坑是行号必须画在背景绘制阶段（画在正文阶段会被裁掉）。参考实现留档在 `docs/research/lightweight-2026-11/poc-reference/TextViewScheme.swift`（测量脚手架已去掉；增删配色在原型里是占位，写反了）。
- **内存要说清楚**：首屏只增加 32–44 MB；但执行「跳到末尾 / 中间」后，进程另有一笔约 120 MB 的增长，1 千行也有、与行数无关，来源未定位。原型进程最终占用 1 千行约 175 MB、1 万行约 215 MB、5 万行约 325 MB（不含位图的一轮）。对照现状看 170 KB 文件后合计 407 MB，**不能断言原生一定更省内存**，实现时须先定位这笔增长。
- 所有绘制耗时都是离屏测量（原型窗口全程未被系统判定为在屏上，原因未查明），真实滚动帧率仍未知。

### 5. 差异数据的来源

- 现状：应用**完全不算差异**，把两份全文交给网页编辑器自己算。换原生后必须补上这一环。
- **推荐以 git 输出为准**：行级用 `git diff -U0`，行内用 `--word-diff=porcelain`，与命令行结果完全一致，零依赖。Apple 没有官方的 Swift 差异算法库（已核实仓库不存在）；系统自带的差异能力做不了行内高亮。
- 750 KB 是应用为网页通道自设的保护线，不是 git 的边界：实测 7.6 MB / 10 万行的文件，行级差异 100–150 ms。
- 实测到 6 个格式坑，实现时必须带上防护参数，例如：用户自己的 git 配置会悄悄改变行内高亮结果；行内输出不能单独承担行结构；仅空白变化时行内有差异而行内为空；`--no-index` 有差异时退出码为 1。
- 行内高亮有两条取法待原型对比：让 git 算（两个临时文件 + 一次额外调用），或像 foldgit 那样对已配对的行自己做有限字符比对。
- 现有读取与缓存约 580 行可保留，数据结构需从「两份全文」改为「改动块 + 行号」。

### 6. 现有差异展示链路

- **仅因用网页而存在**：Swift 594 行、测试 251 行、模型 22 行，加 12.8 MB 资源、约 400 行前端源、Node 构建链、一个常驻监听端口、一个网页渲染进程。
- 每次显示差异的流程：整份文本在主线程打包 → 跨进程传给网页 → 网页重新解析、重算、绘制。24 条缓存只省掉读 git，这一圈每次都重做，大文件会卡主线程。
- 其他问题：大文件和二进制文件是整份读完才判断不展示；监听服务启动若卡住会一直等到重启应用；干净检出无法直接出包（资源未入库，需先装 Node 构建）；冲突文件被拒绝显示的理由与网页编辑器直接相关，换方案后需重新判断。
- 项目文档记录的「这块视图易触发编译器崩溃」从未定位触发原因，且记录于 Xcode 26.3，本机已是 27.2，不能直接当作换方案后的约束。

### 7. AI 提交链路与界面状态层

- 这部分不重，四项核心能力都不用动。点一次「AI 生成」是 1 次请求、1 个候选，没有多轮打分重试。
- 重的是喂给模型前的预处理：约 250 行规则，其中模块权重按本项目自己的目录名写死，换仓库即失效。
- 约 220 行纯死代码；调试面板约 330 行随正式包一起发布。
- 界面状态层健康：选择状态只有一个来源，无定时刷新。
- 模型密钥明文存在本地设置里；仓库里有一份钥匙串读写代码但零调用。

## 五、与路线无关、应先修的问题

| 问题 | 后果 | 修复量 | 复核 |
|---|---|---|---|
| 「双方新增」合并冲突被当成普通新增 | 显示为新增、可勾选、默认提交，等于把带冲突标记的内容提交了（程序只认带 U 的状态码，该场景是 AA） | 2 行 + 测试 | 主控已复现 |
| 文件名含 `*`、`?`、`[` 时被当成通配模式 | 实测暂存 `a*.txt` 时 `av.txt` 被一并暂存 | 1 行 + 测试 | 主控已复现 |
| 提交与推送无超时、无取消；中途失败不恢复暂存区 | 推送卡住时整个界面不可操作；别处暂存好的内容被改写后不恢复 | 中，需先设计 | 代码确认 |
| 侧栏悬停预读无节流 | 划过列表即大量启动 git 进程，占满后台通道 | 约 20 行 | 代码确认，卡顿程度未实测 |
| 差异视图启动即加载 | 不看差异也常驻约 145 MB | 约 15 行 | 基线实测 |
| 主线程打包整份文本 | 大文件切换卡主线程 | 约 15 行 | 代码确认 |
| 监听启动卡住无超时 | 重试永远超时直到重启 | 约 10 行 | 代码确认 |
| 死代码约 220 行 | 无行为影响 | 直接删 | 抽查属实 |
| 文件「智能分组」约 200 行打分，鼠标划过即重算 | 文件多时可能掉帧 | 需先设计 | 代码确认 |

零风险速赢另有：上次扫描结果持久化、启动先展示；状态解析先按字节筛再解码；合并 4 处成对重复代码（净减约 80 行）。

## 六、未验证清单

2. 网页瘦身、换库两档的运行时内存——「辅助进程与常驻内存基本不变」是推断。

### 原生方案把关结果

判据见实施契约（先于测量确定）。测量为按显示器刷新节拍驱动的离屏代理测量，**真实上屏确认未做**。

| 关卡 | 结论 | 要点 |
|---|---|---|
| G1 单栏滚动 | 通过（代理测量） | 1 万 / 5 万行，相邻节拍间隔中位数 16.67 毫秒，超 34 毫秒占比 0–0.5% |
| G2 并排同步滚动 | **不过** | 原型的并排承载每拍主线程工作约 1.24 秒，比单栏慢约 200 倍，原因未定位 |
| G3 内存 | **不过** | 成因已定位：文本视图被撑成文档全高，系统为它到过的区域分块分配位图（约 24–46 块 × 4 MB，与行数无关）。把视图高度钉在一屏后同样操作只增 0.3 MB，但该对照没有真正滚动，且可用的规避办法尚未实现与实测 |

另一个已核实的事实：AppKit 里没有「视口高度、按文档范围滚动」的现成文本视图组件（用编译器实测确认），要解决 G3 必须自己实现一套滚动与跳转机制。

### 决策

按事先约定的规则（两项不过即退到轻量网页库），**当前改走 (b2) 换 CodeMirror 6**，并配合两项与路线无关的优化：差异视图用到才加载、去掉主线程整份打包。

原生方案不是被否定，而是留作后续升级：它还剩两个未解的工程问题（视口高度的滚动与跳转机制、并排承载的性能），且真实上屏验证需要用户不使用电脑的时段。已完成的原生数据层（逐行对照与行内高亮计算）保留在仓库里，改为按需计算、不在日常加载路径上产生开销；是否长期保留列入待决策。
