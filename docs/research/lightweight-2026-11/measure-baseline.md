# NeatGit「重」的基线测量报告（measure-baseline）

> 只读调研：未改仓库任何文件，未动 `/Applications/NeatGit.app`，未执行任何 git 写操作。
> 测量对象是我自己在 `/tmp/swarm/measure/` 下构建并启动的副本。内存单位 MB = 1,048,576 字节。

## 一、结论

1. **包体的「重」几乎全在内嵌网页资源**（已验证）：Release 应用包 16.8 MB，其中 Monaco 网页资源 12.4 MB 占 74%，自家代码编译出的二进制只有 4.3 MB。资源里 8.0 MB 是 5 个「语言后台进程」脚本，其中 TypeScript 一个就 5.76 MB。页面脚本只在文件被识别为对应语言时才加载这些脚本（已验证选择逻辑，`logs/worker-usage.txt`）；应用是否按文件后缀指定语言我没有核实。
2. **运行的「重」是进程数与常驻内存，而不是启动耗时**（已验证）：应用一启动、还没选任何仓库，就常驻 4 个进程，合计内存 204–225 MB，其中网页渲染进程独占约 124 MB，应用主进程 55–80 MB。窗口约 1.1 秒出现，这个数字并不差。
3. **看差异带来的内存增长与文件大小相关，但幅度远小于「第一次」**（已验证）：第一次显示差异让渲染进程从 124 MB 涨到约 169 MB（编辑器初始化），之后 2.8KB → 170KB 的文件把它推到 276 MB；过程中总量瞬时峰值 480–656 MB。辅助进程数量不随操作增加。
4. **本机当前负载很高，耗时类数字噪声大**（已验证）：测量期间 12 核机器负载均值 7–15，「进入空闲」实测 3–19 秒不等。更稳的指标是应用自身消耗的 CPU 总量：启动到空闲合计 1.6–2.6 核·秒，主进程占 52–65%。

## 三、对三条路的直接含义

- 走 (a) 换原生渲染：可直接去掉约 12.4 MB 资源（占包体 74%）和 3 个辅助进程（约 145 MB 常驻 + 首次差异的 +45 MB 渲染初始化）。
- 走 (b) 保留网页路线瘦身：若确认应用不会把文件识别成 TypeScript / CSS / HTML / JSON 语言，裁掉这 4 个后台脚本可省约 7.7 MB（包体减少约 46%）；这一点**未验证**，需要查前端源码里语言是怎么定的。裁文件能减包体，但我预计辅助进程数与常驻内存不会因此明显变化——这部分成本来自「用了网页引擎」本身。后半句是未验证假设。
- 走 (c) 只做架构优化：本基线里可量化的两个点是「未选仓库时渲染进程已常驻约 124 MB」和「首次差异时渲染进程再涨约 45 MB」。把加载推迟到真正要看差异时，能省掉的是「不用差异功能的会话」的这部分，而不是看差异时的成本。

## 四、可复跑的命令清单

全部脚本在 `/tmp/swarm/measure/`，在仓库根执行，产物与日志只写该目录。

| 目的 | 命令 |
|---|---|
| Debug 构建并计时 | `/tmp/swarm/measure/build-debug.sh` |
| Release 构建并计时 | `/tmp/swarm/measure/build-release.sh` |
| 包体与资源占比 | `du -sk <应用包>/Contents/*`；`find <应用包>/Contents/Resources -type f -exec stat -f '%z %N' {} +` |
| 二进制段大小 | `size -m <可执行文件>` |
| 链接的框架 | `otool -L <可执行文件>` |
| 启动测量 | `/tmp/swarm/measure/launch-measure.sh <标签>`（启动 + 到空闲 + 空闲稳定态） |
| 启动结果汇总 | `python3 /tmp/swarm/measure/tools/analyze.py launch <标签>`；`steady <csv>`；`timeline <标签>` |
| 界面选中仓库 | `tools/bin/axtool select <pid> "repository-<仓库完整路径>"` |
| 界面选中文件并计时 | `APP_PID=<pid> MARKS=<标记文件> /tmp/swarm/measure/diffstep.sh <标签> repository-files <文件名> <基准截图>` |
| 各状态内存汇总 | `python3 /tmp/swarm/measure/states.py <标签>` |
| 进程归属核验 | `lsof -nP -a -iTCP -sTCP:LISTEN -p <pid>`，再查谁连了该端口 |
| 扫描成本估算 | `python3 /tmp/swarm/measure/tools/scanreplica.py` |

采样工具源码在 `tools/` 下：`procsample`（内存与 CPU 采样）、`launchwatch`（窗口出现时刻）、`axtool`（无障碍操作）。

**测量口径的两个坑（已验证，复测请沿用）**：
- 内存用「物理占用」（与活动监视器「内存」列同源，已和系统工具对 Finder 交叉核对一致）。
- 系统提供的进程资源统计接口里的 CPU 时间**不含已退出线程**，会少报一个量级（实测 9 秒的已知负载只报 0.2 秒）。本报告 CPU 一律取系统进程列表的累计时间列。

## 五、未能测量的项及原因

| 项 | 状态 | 原因 |
|---|---|---|
| 应用内「仓库扫描」单独耗时与 CPU | 未测，仅有估计 | 尝试用空家目录启动做对照，但应用不认这个环境变量（界面仍列出 12 个分组）。估计值来自按同样规则另写的一段目录遍历脚本，不等于应用内真实耗时 |

## 六、过程中的意外与副作用

- **一次误点击**：副屏在主屏上方，我的坐标换算有误，一次点击落到了主屏底边。已核查：前台应用未变、没有新应用启动。
- **启动注册**：两份副本曾登记到系统启动服务，已按路径注销。
- **偏好设置**：副本与已安装版本共用同一套偏好。我没有收藏仓库、没有改设置，选中状态不落盘。
- **被测仓库**：应用自身读取状态时可能刷新了两个被查看仓库的索引缓存，这是应用的固有行为。
- **检索服务**：外网检索中途触发小时配额上限约 25 分钟，恢复后补做了检索。网页引擎多进程模型的外部来源：https://deepwiki.com/WebKit/WebKit/1.2-core-components 、https://medium.com/@eastism/about-wkwebview-b1eb92d078ca
- **磁盘**：`/tmp/swarm/measure/` 现占约 374 MB（两份构建产物 369 MB，日志 2.1 MB），全部保留，可整体删除。
