# 原生差异视图验证原型：实测报告（poc-native-render）

> 一次性原型，代码与数据全部在 `/tmp/swarm/poc/`。本任务对 NeatGit 仓库只做过只读检查，没有写入；期间工作区里出现的文档改动不是本任务产生的。

## 一、结论

1. **原生方案在万行级够用，前提是选对承载方式**（已验证，离屏测量）。
   - 首选 **方案甲：系统文本视图（TextKit 2）+ 自己补画行号栏和整行底色**。5 万行差异首屏约 0.12 秒，跳到末尾/中间约 0.03 / 0.016 秒，预热后每滚约 0.65 屏主线程工作约 4.5 毫秒，且这三个数字几乎不随行数变化。
   - 方案乙（纯 SwiftUI 懒加载行列表）可用但偏慢：每屏绘制是甲的约 2.4 倍，跳到末尾随行数线性变慢（5 万行约 0.96 秒）。
   - 方案丙（SwiftUI 列表控件）不建议：首屏就与总行数成正比（5 万行 1.2 秒），内存最高。
2. **系统「新文本能力」不能直接做差异视图**（已验证）。
   - macOS 26 新增的富文本编辑器，一万行首屏要 15 秒、五万行 410 秒（随行数平方增长），直接出局。
   - 整个本机 SDK 里**没有任何**行号栏、代码高亮、代码编辑器类型的公开接口；行号只能自己画。
   - 苹果今年展示的「带行号的代码编辑器」做法与我的原型同路（子类化系统文本视图 + 自己画行号），但它依赖的新钩子要 **macOS 27** 起，NeatGit 的部署目标 26 用不上。
3. **未能取到的数字**：真实上屏帧率。正式跑批期间窗口始终未被系统判定为「在屏幕上」（未锁屏、未息屏，原因未查明），所有绘制耗时都是离屏绘制，见第六节。

## 六、问题清单与局限

1. **真实帧率未测**。原因：正式跑批全程窗口的「在屏幕上」状态为假（最早一次诊断时曾为真，之后一直为假；未锁屏、未息屏，疑被其它窗口完全遮挡或在别的桌面空间，未查明）。绘制耗时全部是离屏绘制，真实上屏合成开销与滚动帧率不在数字里。
2. **行号画不进正文绘制阶段**（已验证）：在正文绘制方法里、调用父类之后补画行号，行号栏区域已被裁掉，画了不显示；改到背景绘制阶段才正常。这是甲方案唯一的实现坑。
3. SwiftUI 方案在本机 macOS 26 上底层是系统表格视图，跳转时系统日志报「表格视图委托被重入，将来会变成断言」的警告（已验证，见 `logs/list_*_r*.log`）。
4. 异步忙碌的判定靠主线程 CPU 时间，单轮不足 1.5 毫秒的零散工作不计入，读数偏保守。
5. 甲、丁跳转后那一笔约 120MB、与行数无关的内存增长**来源未定位**（未验证假设：超高文本视图的图层分块后备存储）。不画位图也复现，排除了截图位图的影响。
6. 原型的 SwiftUI 行视图行号栏偏窄，双行号的上下文行会折成两行、行高不均（原型的行设计问题，不是框架限制）；乙/丙的每步耗时因此略受影响。
7. 跑批期间机器上还有其它测量任务，可能有少量噪声。
8. 最终数据取自最后一轮完整跑批的二进制；之后只加了诊断代码和一处访问级别调整，未改测量路径。
9. **未验证**：两栏联动滚动、语法着色、选区/复制/查找、真实文件差异（原型用合成数据）。
